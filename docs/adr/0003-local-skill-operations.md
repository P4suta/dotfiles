# Local Shared-Skill Operations

Status: Accepted.

## Context

Shared instructions need maintained discovery, composition, evaluation, executable enforcement, and native distribution.
Frequency alone cannot establish compliance, eligibility, or whether responsibilities should merge.
An analysis without a required disposition can become a permanent list of unimplemented recommendations.
The operating standard must survive changes in coding agents and review services.

## Decision

Extend the existing Rust xtask with a native `skill-ops` command and a managed capability-based skill policy.
Keep canonical instructions and conditional resources in one tree, with checked aliases and an explicit acyclic prerequisite graph.
Provide named bundles for common tasks while retaining independently useful skills.
Use native client adapters to distinguish explicit loader signals, direct file reads, and weaker shell references.
Store hashed operation identities and catalog revisions without retaining prompts, command bodies, raw session identities, or transcripts.

Publish observations as immutable content-addressed records with synchronized files, atomic publication, and Unix directory synchronization.
Preserve reports and dispositions in immutable local history, with separate current pointers.
Reject corrupt state and conflicting replay rather than resetting history.
Bind each runtime disposition to its exact report and current evidence-file hashes.
Read the accepted report by its verified immutable identity instead of pairing independently updated draft and decision pointers across concurrent sessions.
Capture report identities before scanning immutable local records so a newly published analysis cannot outrun its input snapshot.
Validate newer draft references for missing records while keeping the accepted snapshot subject to current inputs, notes, evidence, and observation thresholds.
Windows file synchronization and atomic publication are exercised natively; the operating system and filesystem remain trust assumptions for power-loss persistence.

Require an evidence-backed disposition for every current catalog and runtime finding.
Allow supported implementation, reasoned retention or rejection, and explicit deferral with a reconsideration condition.
A record proves structural completeness and freshness; the agent remains responsible for the semantic quality and authorized implementation of its decision.
Do not offer a blanket approval command or automatically merge skills from co-use counts.
Drive maintenance from content changes, demonstrated improvement notes, and new observation counts rather than elapsed time.
Bound Stop-hook continuation to one automatic maintenance request and preserve an incomplete outcome when the next check still fails.
Keep the OpenCode observer and shared completion instruction explicit because this adapter lacks an equivalent blocking Stop hook.

Keep the authoritative catalog review, strict adapter typecheck, native regressions, and production proof gate in the existing project checks and required CI.
Bind the maintenance engine to its pinned tool and gate configurations, and keep changing build and dependency outputs outside chezmoi source state so independent native checks can safely run concurrently.
The six Kani harnesses import the actual completion, disposition, composition, maintenance, immutable-identity, and installation-stage decision functions.
They quantify their admitted Boolean and native integer inputs, require reachable outcomes, and check overflow without conclusion-shaped assumptions.
Verify the exact harness inventory and successful properties, and require a deliberately false claim to produce the expected assertion counterexample.
Native integration tests exercise SDK payloads with an empty PATH, concurrent publication, parser failures, evidence freshness, ordered installation, preservation, and external filesystem boundaries.
Execute local Kani hooks on supported Mac and Linux hosts, retain the required Linux CI proof gate for every PR, and verify Windows native contracts without presenting the unavailable verifier as a passing proof.
These decision proofs do not claim to verify the Rust standard library, serialization packages, filesystem, client implementation, or the agent's judgment.

Apply intended files and native executables through each machine's own profile without copying credentials, client trust decisions, or usage history.
Merge collector definitions into existing client settings and require normal native trust and activation checks.
Apply policy before installing the validated native executable, and activate the OpenCode adapter only after installation succeeds.
Resolve the adapter's executable from the native user directory or an explicitly configured absolute path.
Keep third-party and system skills outside the owned dotfiles catalog rather than attributing their use to similarly named owned entries.
Record the reviewed canonical file inventory in the installed manifest and validate every managed file without deleting unrelated native helpers or caches.

## Consequences

A changed catalog, policy, or maintenance engine invalidates the current catalog review.
A pending runtime improvement cannot pass the maintained completion check without a complete current disposition.
Reinstallation preserves observations, notes, reports, and old decisions.
Coverage gaps and implicit client skill injection remain visible limitations of observation counts.
The owner can maintain the same standards through different clients and code-review providers.
New verification capabilities must be selected against actual failure classes and rolled out to compatible projects through reviewable changes.
More client integration and individual proof obligations can be added without replacing the canonical skill tree or historical evidence.
